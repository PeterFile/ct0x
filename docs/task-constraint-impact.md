# Task constraint impact (experimental)

The existing WorkInput command still owns the decision. A proposal does not change the plan. On the first live owner ACK of each constraint-bearing WorkInput (`after_constraint_revision > before_constraint_revision`), the same SQLite transaction records a separate confirmation, a public-only platform notice in the original topic, and exact references to the scoped delegated work and submissions it invalidates. Work recorded between two ACKs can be invalidated by the second ACK, even if its proposal revision or message sequence is lower. A context-only ACK or replay of the same input does not apply a change. Neither order nor a shared excerpt proves that one input supersedes another.

The original Task revision and Mandate are not rewritten. The plan's `before_*` and `after_*` values are that input's original proposal snapshots, numbered by assessment persistence (which may be out of message order). The acceptance basis is the original Mandate; neither proposal snapshot represents an effective-constraint view. The actual ACK remains separate.

The existing scheduler carries the original WorkInput to its owner. Older queued delegations and report wakes cannot start. Already-claimed children still need real settlement; unknown is not a terminal outcome. The owner can repeat a check via the existing scoped delegation command if authority, runtime and budget still permit. A delegated WorkReport is an identified report, not an independent verification result. v30 has no separate durable verification record or verification-based acceptance gate.

When the confirmed plan has earlier formal output (that exact Task revision, or a predecessor identified by an existing direct repair link), direct dependents are matched by immutable Submission and Artifact/version pins. No topic proximity, Artifact head, plain edge, or summary text creates an impact. The stale pin prevents activation, fresh submission and new acceptance; old reviews and receipts remain readable and unchanged. Cancellation is requested only for a known-running, accepted, exact formal owner of an affected revision. Holds and cancellation never release resources or replace an execution. There is no cross-topic notification or wake for the pin hold. The existing runtime cannot replace pins in place, reopen an accepted owner Task for followup, or apply B1 followups to workspace work. Thus the normal live scope here is open text/read-only investigation and its in-scope replan, plus explicitly linked text repair history. The exact artifact pin/owner fence is tested with a predecessor fixture; that fixture is not a supported product entrypoint. Downstream repinning/rescheduling needs separate authorized replanning after real settlement and is not implemented here.

`GET /api/v1/groups/{group}/tasks/{task}/impacts` is a bounded local-user history, using `limit`/`before`. It shows both impacts on that Task and direct downstream effects of its own inputs, together with separate current Task status. A native accepted timestamp (when present) and the actual owner ACK are separate. `ListTaskImpacts` exposes the same `domain.TaskImpact` types to trusted Go callers. C can correlate stale evidence to existing report IDs, and can observe `constraint_impact_stale` on blocked typed wakes. History and terminal receipts are still accessible through the existing reads.

For F, only a `work_input_returned` entry has a `Decision`: the persisted scoped question, reason, policy, member/Turn/Attempt and timestamp. For every impact, `Source` fixes the original message and `source_sequence` (the same committed message sequence as `TaskWorkInput.SourceSequence`), command source, trigger, WorkInput and exact group/topic/Task/revision/Assignment/Mandate/generation. `ScopeCurrent` is an advisory version check, not authority to answer. A stale pin carries the original artifact/Submission/version and Review context for a future explicit replacement decision; it is not itself a decision. No answer endpoint, additional grant, synthetic assessment or pending-item lifecycle is provided by B3.

`taskImpactSchema` is one additive migration, registered once after the release base. It does not backfill effects or handoffs for already handled inputs.
