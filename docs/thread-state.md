# Experimental Thread/Task state (E2)

E2 stores explicit local-human confirmations. It does not derive state from chat, wake anyone, change a Task or Mandate, create a Review, or grant access. The compatibility Thread is the exact `(group_id, topic_id)`; a member's Conversation is only an execution binding. State never crosses groups.

## Local command and reads

Use the existing LocalUser loopback HTTP boundary (the same Host and write-Origin checks as messages; not a member/MCP endpoint):

```http
PUT /api/v1/groups/{group}/thread-state?topic_id=export-bug
Content-Type: application/json
Idempotency-Key: confirm-csv-1

{"expected_revision":0,"slot":0,"kind":"constraint","action":"set","content":"必须兼容旧版 CSV","source_message_id":"<message-id>","covered_through_message_id":"<coverage-message-id>"}
```

- `topic_id` is exact, including whitespace; absent or empty means the main topic, not all topics. To address Task state, include both `task_id` and `task_revision`. The Task must be in the group and linked to the exact topic by `task_coordination` and its persisted Mandate. No task-link table is added. An unlinked Task or a same-group Task from another Thread does not qualify. Task versions have independent state; do not silently carry an old confirmation into a new Task version.
- Slots `0..7` are explicit records. The first write fixes the slot's kind: `goal`, `constraint`, `confirmed_decision` or `plan`. Editing one slot cannot overwrite another. `set` writes an active value; `invalidate` retires an active value and stores its reason, keeping the original value and source. An occupied plan slot cannot be reused, even after retirement. Retire a superseded plan and use an unused slot for its replacement; both remain in the current handoff. The slot bound still applies.
- Each value or invalidation reason must be the complete, non-blank text of an existing `local_user_chat` message in that Thread, byte-for-byte (including whitespace), at most 1024 UTF-8 bytes. Do not confirm excerpts: a negation or quotation is part of the evidence. For a long message, write a separate short confirmation in the same Thread. A displayed `user` sender, member assertion, or platform notice is not sufficient. No Review or WorkInput is accepted by this slice. The server binds the actor, resolves the command-source ID and `message_log` position, and stamps the confirmation. A new change to an existing slot needs a strictly later source position for that slot.
- Optional `covered_through_message_id` explicitly sets the inclusive coverage position for the whole exact state scope. It must be a message in the same group/topic with a verified `message_log` entry, independently of the confirmation source. Its position may stay the same or advance; omission preserves prior coverage. `null` and an empty string are invalid. This is a local-user boundary for selecting history, not a summary, read or consumption receipt, or grant.
- A successful command returns `200` and the immutable snapshot at `expected_revision + 1`. Compare-and-append and the group/actor/operation-scoped idempotency receipt commit together. A retry with the same key and input returns that snapshot even after unrelated state updates; it still checks access and the Task version. Explicit coverage participates in the key payload; omission is not equivalent to explicitly naming the inherited anchor. A changed payload conflicts (`conflict`); stale CAS, Task version, slot lineage or coverage rewind conflicts (`thread_state_conflict`). An inaccessible source, coverage message, Thread, Task link or historical snapshot returns `404`.
- `GET` on the same URL returns `{scope, revision, records}` and, when explicitly set on or before that revision, `covered_through: {message_id, message_log_position}`. Reads recheck that exact message and position against the scope and reject a damaged anchor. Revision `0` with `records: []` means no state or coverage in an existing Thread/scope. Add `revision=N` (positive) to read the snapshot as of that state revision; an explicit historical read may use an older `task_revision` if the Task still has the exact verified link. Current reads and all writes require the current Task version. `records` are ordered by slot and carry their own last change `revision`, `active`, content and `source`. Invalidation adds `invalidated_by: {reason, source}`; `source` still points to the original. The record at the snapshot revision identifies the last command's evidence (its `invalidated_by.source` for retirement). Reads check the exact scope's revision range for gaps and against an independent durable head, advanced in the revision transaction. Losing the last revision or the head does not turn an existing scope into an empty one. Reads also verify the original message and typed source of every returned value and invalidation.

## Preparation and integration

- Ordinary preparation goes through `Preparer.Prepare` → `ordinaryThreadContext` → `Store.LoadThreadPreparation`. State and history share one read transaction after the existing queue/member/Conversation binding. With explicit coverage, take up to the usual 50 candidates from the exact group/topic's indexed `message_log`, strictly after the covered position and strictly before the trigger's position. Display timestamps do not affect this window. If coverage reaches or passes the trigger, the optional window is empty; the trigger and current state still arrive. Without an explicit mark, the previous `(created_at, id)` history path is unchanged. `ContextPack.Source.Sequence` stays snapshot-local; neither the state revision nor a confirmation source's position implies coverage.
- `attachOrdinaryThreadState` fills `contextpack.Input.{StateScope,ThreadState}` only for nonempty state. The byte budget fits mandatory state and trigger first, then a newest suffix of candidate references and the recent bodies that fit. Omission is not coverage. Packets without state retain legacy summary coverage, mandatory overflow references, and wire format.
- With the schema installed, `scheduler.PreparedExecution.PreparedThreadState` carries the exact Thread, trigger ID and state revision, including zero. The existing scheduler forwards it to `Store.ClaimTurn`. Under the claim transaction's write lock, a changed scope or revision returns `ErrTurnBusy` and rolls back before any Turn or resource claim. The delivery is prepared again on a subsequent scan. Claim is the start-admission boundary; later confirmations do not cancel an admitted turn, and claim is not an adapter acceptance or consumption receipt.
- **E1:** `ordinaryThreadContext` is the scope-selection seam. Today it supplies the immutable trigger's exact `ThreadRef`. Effective attribution and corrections must use the same verified scope in history, state, confirmation/coverage validation and the `verifyPreparedThreadStateInTx` claim fence. Do not reinterpret old state or broaden visibility on correction. If E1 adds authoritative Task links, replace the compatibility relation in `threadStateTaskRelation` and its SQL insert guard; do not add duplicate links or treat one as a grant.
- **C / formal roles:** the ordinary hook runs before provider handoff and does not change native or CLI configuration. Keep `PreparedThreadState` on the existing `PreparedExecution` through the scheduler. A role profile that already authorizes the exact Task view can call `Store.LoadAuthorizedTaskThreadState` before rendering. It is a peek, not a claim or launch permission. Typed profiles and delegates need their own disclosure check and claim-time fence for the authorized Task version and state; do not reuse the ordinary Thread stamp for this. No formal role prompt or tool grants are wired here. Native end-to-end delivery must be validated by C.

## Migration and verification

`internal/store/thread_state_schema.go` defines `threadStateSchema`. B should append it to the migration registry in actual merge order. No public number, legacy backfill, or registry edit is part of E2. On uninstalled databases explicit commands return `503 thread_state_unavailable`; existing message and execution preparation paths remain available. Broken installed state fails closed instead of being treated as empty or legacy.

To test installation, copy `internal/store/migrations.go` outside Git, append `threadStateSchema` at the end of its migration slice in the copy, and use `go test -overlay` to replace that path. Run `TestThreadState*` in `./internal/httpapi`, `./internal/platform`, `./internal/store` and `./internal/contextpack` with the overlay, and `TestThreadStateUnavailableOnV30` with the unmodified registry. This tests the actual v30 baseline and the candidate registration without committing a version. The handoff fixture builds a real provider-independent prompt; it does not launch a model. E1 routing, E3 project knowledge, and the real-model 200-message scenario are separate evidence.
