# Experimental Thread/Task state (E2)

E2 stores explicit local-human confirmations. It does not derive state from chat, wake anyone, change a Task or Mandate, create a Review, or grant access. The compatibility Thread is the exact `(group_id, topic_id)`; a member's Conversation is only an execution binding. State never crosses groups.

## Local command and reads

Use the existing LocalUser loopback HTTP boundary (the same Host and write-Origin checks as messages; not a member/MCP endpoint):

```http
PUT /api/v1/groups/{group}/thread-state?topic_id=export-bug
Content-Type: application/json
Idempotency-Key: confirm-csv-1

{"expected_revision":0,"slot":0,"kind":"constraint","action":"set","content":"必须兼容旧版 CSV","source_message_id":"<message-id>","covered_through_message_id":"<coverage-message-id>"}
```

- `topic_id` is exact, including whitespace; absent or empty means the main topic, not all topics. To address Task state, include both `task_id` and `task_revision`. The Task must be in the group and linked to the exact topic by `task_coordination` and its persisted Mandate. No task-link table is added. An unlinked Task or a same-group Task from another Thread does not qualify. Task versions have independent state; do not silently carry an old confirmation into a new Task version.
- Slots `0..7` are explicit records. The first write fixes the slot's kind: `goal`, `constraint`, `confirmed_decision` or `plan`. Editing one slot cannot overwrite another. `set` writes an active value; `invalidate` retires an active value and stores its reason, keeping the original value and source. An occupied plan slot cannot be reused, even after retirement. Retire a superseded plan and use an unused slot for its replacement; both remain in the current handoff. The slot bound still applies.
- Each value or invalidation reason must be the complete, non-blank text of an existing `local_user_chat` message in that Thread, byte-for-byte (including whitespace), at most 1024 UTF-8 bytes. Do not confirm excerpts: a negation or quotation is part of the evidence. For a long message, write a separate short confirmation in the same Thread. A displayed `user` sender, member assertion, or platform notice is not sufficient. No Review or WorkInput is accepted by this slice. The server binds the actor, resolves the command-source ID and `message_log` position, and stamps the confirmation. A new change to an existing slot needs a strictly later source position for that slot.
- Optional `covered_through_message_id` explicitly sets the inclusive coverage position for the whole exact state scope. It must be a message in the same group/topic with a verified `message_log` entry, independently of the confirmation source. Its position may stay the same or advance; omission preserves prior coverage. `null` and an empty string are invalid. This is a local-user boundary for selecting history, not a summary, read or consumption receipt, or grant.
- A successful command returns `200` and the immutable snapshot at `expected_revision + 1`. Compare-and-append and the group/actor/operation-scoped idempotency receipt commit together. A retry with the same key and input returns that snapshot even after unrelated state updates; it still checks access and the Task version. Explicit coverage participates in the key payload; omission is not equivalent to explicitly naming the inherited anchor. A changed payload conflicts (`conflict`); stale CAS, Task version, slot lineage or coverage rewind conflicts (`thread_state_conflict`). An inaccessible source, coverage message, Thread, Task link or historical snapshot returns `404`.
- `GET` on the same URL returns `{scope, revision, records}` and, when explicitly set on or before that revision, `covered_through: {message_id, message_log_position}`. Reads recheck that exact message and position against the scope and reject a damaged anchor. Revision `0` with `records: []` means no state or coverage in an existing Thread/scope. Add `revision=N` (positive) to read the snapshot as of that state revision; an explicit historical read may use an older `task_revision` if the Task still has the exact verified link. Current reads and all writes require the current Task version. `records` are ordered by slot and carry their own last change `revision`, `active`, content and `source`. Invalidation adds `invalidated_by: {reason, source}`; `source` still points to the original. The record at the snapshot revision identifies the last command's evidence (its `invalidated_by.source` for retirement). Reads check the exact scope's revision range for gaps and against an independent durable head, advanced in the revision transaction. Losing the last revision or the head does not turn an existing scope into an empty one. Reads also verify the original message and typed source of every returned value and invalidation.

## Preparation and integration

- `Preparer.Prepare` → `ordinaryThreadContext` → `Store.LoadThreadPreparation` keeps the exact bound delivery and trigger. In one read transaction, select the stored state for that Thread, recheck which proof can be shown, verify explicit coverage, and select/project ordinary history using E1b effective membership. A correction does not rebind the trigger, a state slot, a Task, or any grant. Correction commands are not candidates.
- In ordinary prompts, a latest slot is shown only if its original and (for retired records) retirement evidence still match effective scope and neither was moved since its respective confirmation. A move out and back is still a change. Otherwise omit the record, never select an earlier revision of its slot; keep the stored revision for claim. Local GET/replay and verified formal state reads keep the immutable storage-scoped evidence. New ordinary confirmations and explicit marks require both the exact stored scope and current ordinary visibility. A fresh message in the bound topic can confirm a new value, subject to the same slot rules.
- A verified mark uses the topic's indexed `message_log` strictly after the covered position and strictly before the bound trigger, excluding corrected-out bodies and correction commands before the limit. If the mark reaches or passes the trigger, the optional range is empty. A move into the topic committed *after the marked log position* may reveal an older message not covered there. Do not apply the mark in that case, when its anchor is no longer visible, when state evidence was omitted, or when the indexed proof is incomplete (at most 128 incoming-move receipts are checked). Fall back to the same E1b recent-history window (`(created_at, id)` before the trigger, up to 50 by default); a very old corrected-in message outside that window is not guaranteed to appear. No larger catch-up range, inferred coverage, or summary. A new explicit anchor after the change can restore the log window when verifiable. `ContextPack.Source.Sequence` stays snapshot-local.
- `attachOrdinaryThreadState` fills `contextpack.Input.{StateScope,ThreadState}` for a nonzero state revision. The byte budget fits mandatory state and trigger first, then a newest suffix of candidate references and bodies. Omission is not coverage. Packets without state retain the legacy budgeting and wire format.
- The ordinary stamp on `scheduler.PreparedExecution.PreparedThreadState` includes the exact Thread, trigger, state revision (including zero) and a cursor into the committed correction ledger. Under the existing claim transaction's write lock, a different binding or state revision or a newer real correction touching the bound group/topic returns `ErrTurnBusy` before any Turn or resource claim. An unchanged correction tip costs one indexed lookup; when it advances, check at most 128 new receipts and retry conservatively if the tail is longer. Unrelated moves and no-op receipts in a complete tail do not block admission. E1b-only installs also get this correction fence. The delivery stays queued for re-preparation. Claim is the start-admission boundary, not an adapter acceptance or consumption receipt; later changes do not cancel admitted turns.
- If E1 adds authoritative Task links, replace the compatibility relation in `threadStateTaskRelation` and its SQL insert guard. Do not add duplicate links or treat one as a grant.
- **Formal first turns:** the existing non-typed coordinator and assigned worker profiles include confirmed state for their exact Task version. This includes the workspace profiles and a new repair Task, never the repair parent's state. Task state uses the same role packet budget and keeps stored evidence; its coverage does not change the role's stored Thread history. An ordinary or repair intake, typed investigation, follow-up, report, or delegate does not get this Task view. Neither a shared group nor a shared Thread authorizes it.
- Formal preparation uses the same authorized read as `Store.LoadAuthorizedTaskThreadState` to issue the formal claim stamp (including when E2 is unregistered or empty). Before inserting a Turn or resource claim, `ClaimTurn` rechecks the reserved delivery's exact role, request, assignment, Task version, current readiness, return/typed markers, and E2 state revision or integrity. A stale claim rolls back for re-preparation. This check does not replace execution-time authorization or change the provider bridge, grants, or tools.

## Migration and verification

`internal/store/thread_state_schema.go` defines the private `threadStateSchema`, including the committed correction cursor saved on each ordinary confirmation. It can install without E1b; those confirmations have cursor zero. The changed schema is for fresh private composition installs, not an upgrade of a database already stamped with the earlier private E2 SQL. B owns the public registry and any eventual public upgrade. On uninstalled databases explicit commands return `503 thread_state_unavailable`; existing message and execution preparation remain available. Broken installed state fails closed instead of being treated as empty or legacy.

Public v43 already registers `threadRoutingSchema` and `threadCorrectionSchema`. Before B registers E2, verify composition by copying `internal/store/migrations.go` outside Git, appending only `threadStateSchema`, and pointing `go test -overlay` at that copy. Run `TestThreadState*` and `Test*ThreadCorrection*` in `./internal/httpapi`, `./internal/platform`, `./internal/store` and `./internal/contextpack` with the overlay. Run `TestThreadStateUnavailableOnV30` and `TestThreadStateMissingOwnMarker` with the unmodified registry to check availability and fail-closed behavior. These fixtures exercise the store, local-user commands, prompt builder and claim without launching a model. The real-model 200-message scenario requires its own run.
